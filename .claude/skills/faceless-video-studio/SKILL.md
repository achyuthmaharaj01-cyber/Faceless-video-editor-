# faceless-video-studio

Script + voiceover in → edited video out. **HyperFrames** composes and renders; **VideoHub** is where the user
reviews before anything is rendered. You (Claude) are the director: the tools measure, align, build, check and
render; you make the creative decisions with the style guide.

## 0. Locate the studio and check the machine

The studio is this repository (`bin/fvs.mjs`). If you are not inside it, use `$FVS_HOME`. All commands below are
`node <studio>/bin/fvs.mjs …` (shown as `fvs …`).

```bash
fvs doctor
```
Fix anything marked missing before starting (it prints the exact install command). Do not install system
packages or change the user's machine without asking.

## 1. Inputs (ask only for what is missing)

Needed: the **script** (.txt/.md/.docx) and the **voiceover** (.wav/.mp3/.m4a/.aac). Optional: title, format
(`long` 1920×1080 default, `short` 1080×1920), a licensed music track.
- Files on disk: use them.
- Google Drive: with the Google Drive connector, `search_files` in the user's input folder
  (`YouTube Production/Input/`), pick the newest script + audio pair, download with `download_file_content`
  into a scratch folder. Do not assume a Drive link grants access; if the connector is missing, say so and ask
  for the files another way. See `docs/google-drive.md`.
Never ask for something you can read from the files (duration, title heading, sample rate…).

## 2. Create the project and analyse

```bash
fvs new "<name>" --script <script> --voice <voiceover> [--format short] [--workspace <VideoHub films folder>]
fvs analyse <project>
```
- Put projects in a folder VideoHub watches (on the user's PC: the VideoHub films folder from `hub_workspace`).
- `analyse` aligns the script's words to the voiceover (faster-whisper). Read `analysis/alignment.json`
  `mismatchesNeedingReview`: a skipped sentence or a **number that differs** between script and voiceover must be
  shown to the user. Never "fix" the narration; the voiceover is the timing authority.

## 3. Storyboard (the creative step — do it properly)

```bash
fvs storyboard-draft <project>
```
The draft is mechanical. **Rewrite every scene** in `storyboard/storyboard.json` using:
- `references/reference-analysis/master-style-guide.md` (read it every time) and the guide that fits each scene
  (visual-storytelling, motion-graphics, transitions, typography, colour, sound).
- `docs/storyboard-schema.md` for every visual/layer/transition type and its options.

For each scene decide: what the narration says → the most concrete honest picture → one explanatory layer →
camera move → transition → sounds. Time overlays to spoken words with `"@word"`. Vary formats; make numbers
physical; no on-screen figure that the script does not state; no look-alike portraits.

```bash
fvs storyboard-check <project>      # must pass: contiguous, covers the voiceover, script order
```
Write `storyboard/storyboard.md` is regenerated by build; show the user a short summary of the plan only if they
asked to approve the storyboard first.

## 4. Assets (licensed, verified, registered)

For scenes that need media, find candidates and **look at them** before choosing:
```bash
fvs asset-search --query "<specific subject>" --sheet <scratch>/c.jpg --save <scratch>/c.json --brief
```
Open the sheet image, pick by relevance first (then resolution), and put the chosen candidate object in the
scene's `assets[].pick` (or leave `query` for automatic choice). Then:
```bash
fvs assets <project>
```
Rules (docs/asset-licensing.md): only commercial-use + modifiable licences (CC0, public domain, US-gov, CC BY,
Pexels, Pixabay); CC BY-SA/NC/ND/unknown are refused; every file goes into `assets/asset-licence-register.csv`.
Never download pirated media, bypass paywalls/DRM or remove watermarks. Paid stock or paid AI image generation
needs the user's approval first (state the cost). If nothing suitable is licensed, design an original visual
(map, document, kinetic text, 3D, code-drawn illustration, or a `custom` composition).

## 5. Build and look at it yourself

```bash
fvs build <project> --reason "<what changed>"
npx hyperframes lint <project>                    # 0 errors
npx hyperframes snapshot <project> --at <one time per scene> --no-end
fvs qc <project>                                  # pre-render: layout, figures, licences, storyboard
```
Open the snapshot contact sheet and **look**. Fix anything wrong (layout, empty frames, unreadable text,
irrelevant images) before showing the user. Every build snapshots the previous version into `versions/`.

## 6. Review in VideoHub (mandatory before any final render)

If VideoHub's MCP tools (`hub_live`, `hub_notes`, `hub_note_update`, `hub_project`, `hub_render`, `hub_job`,
`hub_workspace`) are loaded, use them; otherwise the same tools run as
`node <VideoHub>/server/cli.js <tool> '<json>'`. Do not invent tool names.

1. `hub_live({project})` → tell the user to watch, scrub and leave notes, then press "Send to Claude". **Stop and wait.**
2. When notes arrive: `hub_notes({project})`, then `fvs notes <project>` — it restores each live note's picture
   from a real HyperFrames frame and gives you the storyboard scene and narration at that moment. Open the
   pictures (crop first).
3. Fix in the storyboard (preferred) or directly in `compositions/sNN.html`; then `fvs build` (or
   `fvs preview` after a hand edit of index.html). VideoHub reloads the preview by itself.
4. **Verify each fix** (snapshot at the note's time, look at it) — only then
   `hub_note_update({project, id, status:"fixed", reply:"one sentence"})`.
5. Repeat until the user explicitly approves. Keep every note; never mark one fixed that you did not verify.

Remote/phone review (VideoHub is local-only; never expose port 7788): see `docs/remote-review.md`.

## 7. Approval, final render, quality control

Only after the user says they approve (in their own words):
```bash
fvs approve <project> --by "<user, how/where they approved>"
fvs render <project>           # HyperFrames, 1080p30 H.264/AAC; refuses without a matching approval
fvs qc <project>               # writes reports/quality-control-report.md
```
Never record an approval the user did not give. A render the user starts with VideoHub's Render button also runs
HyperFrames (`render.mjs`). If QC fails, fix, show the change in VideoHub, and get approval again (the approval is
tied to the exact composition). Report QC honestly: failed / warnings / manual review.

## 8. Deliver

```bash
fvs deliver <project> [--to <folder>]
```
Upload `deliverables/` to Google Drive (`YouTube Production/Completed Videos/<title>/`) with the Drive connector
when configured (docs/google-drive.md), including `attributions.txt` (credits for the description).

## 9. Learn (carefully)

After the project, append what the user corrected to `learning/production-log.md`. If a correction is a
*reusable preference* (they would want it in every video), propose it in `learning/style-amendments.md` and ask
before changing any guide in `references/`.

## Costs and approvals

Free by default (local tools, open media, synthesised SFX). Ask first, with the price, before: paid stock media,
paid AI image/music generation, cloud rendering on a paid account, anything with a subscription.
